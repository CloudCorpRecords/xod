### The cause chain (every link from a log line, a state file, or a measured artifact)

### Hardening (committed `b5ee2ba4`; guardian half also deployed live, see below)

**Update guardian — `partner/partner_updates.py`:**
- **Freshness gate:** a rollback may only restore the snapshot of the install the payload actually replaced. A stale/missing snapshot → the new install is left in place, the payload is blocked, and `guardian-report-<version>.json` is written. (Kills step 6's failure mode categorically.)
- **Confirmation battery:** one failed battery never rolls anything back; the battery re-runs once and only a second consecutive failure acts. (Kills step 5's failure mode.)
- **Put-back:** if a restored build cannot start at all (health fails) while the replaced build had passed health, the replaced build — kept aside during the restore — is put back. A restored build that answers health but fails agent probes stays (it is a working app). (Kills step 7–8's "dead app left installed" outcome.)
- **Volatile-tolerant verification:** snapshot/restore verification ignores `__pycache__`, `*.pyc`, `*.log` — the paths a running app rewrites mid-copy. (Kills step 3's failure mode.)
- **Honesty:** a payload with no verified snapshot of the current install logs `ROLLBACK PROTECTION UNAVAILABLE` up front; `status()` exposes `pending_snapshot_ok` and `last_guardian_report`.

**Bootstrap — `electron/bootstrap.js`:**
- **Verify before swap** already existed (checksum vs SHA256SUMS.txt + the asar require-walk + version match on the staged copy) and is unchanged.
- **Verified swap:** every healthy packaged launch now writes `bootstrap-health.json` (version + time) into the data dir, and the macOS repair swap script waits up to 120 s for a *fresh* marker naming the new version before deleting the previous bundle. No marker → the script restores and relaunches the previous install itself and logs it. Previously the backup was deleted the moment any app.asar existed.
- **Attempt counter:** repairs against the same installed version are counted in the data dir (`bootstrap-repair.json`, which no swap touches). After **3**, the bootstrap stops offering repairs, writes `bootstrap-repair-report.txt`, and shows one "repairs are paused" dialog instead of looping. A healthy launch clears the count.

- **The installed bootstrap is pre-hardening until a release ships** (above). ## Part 4 — policy change: rubber-stamp, and the 1.1.15 release (2026-11-22, ~13:51 PT)

The loop's first real in-process judgment came back "leave" on a browser card, and the owner's decision followed at once: judgment must never block a press. The product promise is the reason — the user approved Xod once, so Xod does not ask them to approve the same work again. Approve once, never again.

- **The gate no longer decides.** services/muse_review.py is rewritten as a policy stamp: in act mode (now the shipped default — a machine with no stored setting stamps) every showing of a card gets verdict {decision: approve, policy: rubberstamp} issued locally. The model call is removed from the press path entirely, so latency, key availability and malformed answers can never gate, delay or veto a press. The audit still records each card, the stamp, the action taken and the panel re-read verification (the watcher's _review_outcome is unchanged). Decide mode remains the pause (stamped and logged, nothing pressed), the watcher's own pause still holds every press, and off restores the pre-approver behavior exactly.
- **Tests rewritten to the promise** (tests/smoke/run_muse_review_test.py): the shipped default presses an ordinary card, a card a reviewer would deny, and a card a reviewer would leave; with the model route poisoned to raise, the card is still pressed and a counter proves the press path never calls the model at all. Pause, decide, off, one-stamp-per-showing, audit rows and the Partner verb picks are covered as before.
- **Release mechanics, stated plainly:** the first v1.1.15 tag (created 13:47 PT on the pre-policy tree) triggered release run 45074052636; the owner changed the policy while it was building, the run was cancelled before anything published (no v1.1.15 release or draft ever existed on GitHub), the tag was deleted, and the tag was recreated on the rubber-stamp tree. ## Part 5 — option widgets get the AI review (2026-11-22, ~14:11 PT)

The owner's clarification that split the two press systems: approval cards are a pure rubber stamp (Part 4), but the Muse chat OPTION WIDGETS — the dotted tap-choice buttons his agents raise in chats, the ones that demand his response across too many chats — "are the ones that should be using the AI to review and click the right ones." services/muse_options.py (shipped in v1.1.14 with keyword scoring) is upgraded accordingly. Build/test only in this lane: nothing pushed, tagged, released or installed; the change rides the release AFTER v1.1.15.

- **The pick is now a model verdict.** scan_tree checks the muse_auto_approve switch first (off/paused/away holds without ever consulting the model), then calls the review: `llm_service.chat_completion` in-process on the running backend's own model route, no tools, strict JSON out — `{"pick": <0-based index or null>, "reason": "<one short line>"}` — validated with the approver's old discipline (partner_brain shape rules; a malformed answer is a malfunction, never a decision). The prompt decides as the owner's proxy: prefer the option that authorizes the most work / broadest scope when options differ in scope; never pick a deferral or no-op option when an action option exists. review_sync mirrors muse_review's: bound backend loop when there is one, throwaway loop in a helper thread otherwise, 60s model timeout / 75s gate wait.
- **Failure holds, always.** Model error, timeout, garbage, or the model itself returning pick null ("no clear pick", with its reason) → nothing pressed, hold reason logged. There is deliberately NO fallback to the heuristic score: a widget is an instruction to an agent, and a wrong press is worse than a hold. The heuristic scorer still runs for the log only (the record keeps the question, every option with its score and factors, the model's name and reason, and the read-back), and a test proves the model's pick is pressed even when the heuristic tops a different option.
- **Removed holds.** The blanket protected-topic hold (password/payment/contract/credentials/2FA) is gone — per the owner's permissionless stance the model judges those widgets on their merits, reason logged (a payment widget is now decided and pressed in tests). The ambiguity hold is gone too: resolving ambiguity is the model's job; the only ambiguity-shaped hold left is the model itself returning no clear pick.

## Part 6 — escalate-to-Tree fallback (2026-11-22, ~14:41 PT)

- **Provenance, stated plainly:** the code below was built by a delegated lane in this worktree on top of dc6b2a87. Before the lane finished its planned test pass, the owner ordered the release pushed immediately, and the main session swept the lane's in-tree work into release commit **ca2c727b** ("Release 1.1.16: widget AI review picks, escalate-to-Tree fallback") and shipped it. - **New module: app/services/muse_escalate.py.** Four escalation kinds: `option_widget_held` (an app option widget whose AI review failed or returned no pick), `option_widget_unpressable` (review picked an option but the AXPress itself failed), `card_press_unverified` (a stamped card whose press did not verify), and `chrome_card_unpressable` (best effort Chrome surface, below). An escalation id is `museesc-` plus a sha256 prefix of kind and target id. Dedupe is a live set keyed by that id: one escalation per showing, never more. `expire(target_id)` clears the dedupe entry and closes the audit row, so a genuinely new showing of identical text can escalate again. `escalate()` never raises into its callers; on a transport exception it returns None and does NOT record the dedupe entry, so the next scan retries (mirroring the options failed-review pattern); a send that lands in the local outbox as "queued" DOES count as escalated, because it drains to Tree later.

A plain send with no extra still carries exactly the original seven fields. ## Part 7 — the 1.1.16 guardian rollback: diagnosis, probe fix, and the recovery plan for the owner's Mac (2026-11-22, ~15:15 PT incident; fix built the same day)

**What happened in the field.** v1.1.16 published cleanly (release live, DMG hash matching SHA256SUMS, check_asar green) and the Mac updater installed it; the app cold-launched healthy (bootstrap-health 1.1.16 at 15:10:59 PT). At 15:15:13 the Partner update guardian rolled it back to the file-swapped 1.1.14 and blocked the version. The block record (~/Library/Application Support/XodPartner/blocked-update-1.1.16.json) names exactly one failure: "file round trip: file task ended with status 'failed'". At that moment the backend was under load (a burst of mail-endpoint HTTP 429s plus recall indexing in desktop-server.log).

**Diagnosis.** The rollback came through the ordinary battery path in _maybe_verify_swap, not the mixed-install path (that path's failure string would have led with the version-agreement check; the record leads with the file probe). The shipped code DID contain the confirmation battery, and it did not help, for a structural reason: the file round-trip probe is not an independent witness. It creates an agent task through the very backend it is judging (POST /api/tasks; the model must perform the file write), so when the agent stack is overloaded the task ends 'failed' before anyone has looked at the file. The old probe counted that outcome as a build failure ("file task ended with status %r" for any status other than done), and the confirmation battery re-ran the same probe through the same overloaded task system, so the same false failure came back a second time and the rollback fired. A content mismatch, the only file result that is actually evidence about the build, is observable only when the task completes and the bytes differ; a task-end failure carries no verdict on the bytes at all. One more gap the incident exposed: the old block record carried only the final failure string in a shape identical across guardian builds, so the record alone cannot say which battery failed or which code produced it. On the Mac there is also a partner_updates.py.bak-2026-11-22-pre-hardening file beside the deployed guardian file: the hardened file was swapped in on disk that morning, but xod_partner.py imports partner_updates once at process start, so whether the running Partner judged 1.1.16 with the pre-hardening code (no confirmation battery at all) or the shipped code (confirmation battery, same fate-sharing probe twice) cannot be told from the record, and both builds share the defect that mattered. The fix therefore stamps every block record with the guardian build that acted.

**The fix** (partner/partner_updates.py, guardian build stamp 2026-11-22-probe-fix-1, branch tree/guardian-probe-fix-2026-11-22):
- **Three-valued batteries.** A check verdict is pass, fail, or inconclusive. A battery fails only on evidence about the build (wrong chat reply, wrong file bytes, a dead health endpoint). A battery with no failed check but an inconclusive one is inconclusive: the update is neither accepted nor rolled back, the pending verdict waits, and the battery re-runs on a later tick, gated by a retry interval (update_battery_retry_min_s, 120s) so a struggling task system is not hammered. A conclusive failure anywhere in a battery dominates an inconclusive probe elsewhere in the same battery.
- **The file probe separates the task system from the file.** One attempt returns pass (task done, bytes exact), fail (task done, bytes wrong or the file absent), or inconclusive (task ended failed or cancelled, the task API errored, the task vanished, or no terminal state arrived in time). Inconclusive attempts retry in place with backoff (update_file_probe_retries, update_file_probe_backoff_s) and can only ever report inconclusive, never a counted failure. A content failure is conclusive for its battery and its retry is the confirmation battery.
- **Every rollback path is confirmation-gated.** The mixed-install path no longer rolls back on a single version-agreement read: it runs a confirmation battery and re-checks agreement first, accepts when both come back clean, holds unverified when the confirmation is inconclusive, and rolls back only when the confirmation also fails. (Chosen over always holding a mixed install unverified: a disagreement that survives a full confirmation battery and a re-check is a genuine defect state, not a transient, and leaving a known-mixed install in place indefinitely is the worse failure.)
- **Records that diagnose themselves.** Every block record and marker now carries the full battery history (each battery's which, verdict, and per-probe results), failed_battery, and guardian_build; guardian status exposes guardian_build, last_battery_verdict, and blocked_batteries alongside the existing fields.

**Tests.** The hardening suite gained the two incident shapes. Case D replays this incident (health, chat, and permissions pass; every file task ends 'failed'): against the 1.1.16 guardian it fails at the assertion "a task-system failure rolled back a healthy install"; against the fixed guardian the install is held unverified, an immediate re-tick is gated, and once the task system recovers the re-run battery accepts the update in place. Case E pins the other side: a content mismatch in both batteries still rolls back byte for byte, and the block record carries both batteries, failed_battery "confirmation", and the guardian build stamp. Suites: partner updates 13/13 scenarios, hardening 5/5 cases, muse_options 18/18, muse_review 24/24, muse_app 66/66, muse_chrome 16/16, muse_connect 21/21. One harness repair rides along, called out plainly: run_partner_updates_test.py's rollback scenario shut its fake backend down mid-scenario and ran its second half against a dead server, passing for months only because the old guardian treated every timeout as a failure; the stray shutdown is removed and the scenario now tests what its comments say. (run_partner_repair_test.py fails identically on the base commit and on this branch, in Partner approval-compatibility code this fix does not touch; it is a pre-existing failure, recorded here so it is not mistaken for a regression.)
